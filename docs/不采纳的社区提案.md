维护者可以在新证据出现后推翻其中任何一条——推翻时请在这里追加一段，而不是删掉旧结论。

## #72 Jev 技能自动审批 —— 不采纳（2026-11-25）

**是什么**：为"技能被提议修改"加一条自动审批链路（新 API、新配置、审批 UI），让 AI 可以不经人工确认就改动技能库。

**为什么不采纳**：

1. **产品语义未定**：社区同学（#74）指出，PR 把 `gate` 字段放进 `memory_suggest` 的返回值，但该工具的 `output.schema` 是 `additionalProperties: false` 且只声明了 `ok`/`message`/`queued`——合并后每次成功调用都会报 `ToolCallError`。要修就得先决定"gate 到底是不是工具输出的一部分"。
2. **归档口径未定**：同一 PR 在 `memory_suggest` 的 target 枚举里加了 `project-archive`（22 处），而本仓库 `archive` 动作只覆盖 memory / user / key 三轨，project 轨**没有可逆归档**。要合并就得先实现 project 轨的归档 + 转正，那是另一个功能。
3. **默认关闭、不做也不影响任何人**：`skillJevApproval` 默认 `false`，现状没有任何人依赖它。
4. **安全边界**：这条链路的收益是"少点一次确认"，代价是"AI 可以自己改自己的技能库"。在一个跑在宿主进程内、能读记忆文件与调 shell 的插件里，这个交换不划算。

**替代方案**：需要减少确认噪音时，用现有的 `reviewMode: 'suggest'` + 待确认队列（memory Tab 里可以批量采纳），或者 `skillReviewEnabled` 关闭技能评审。真要自动化，应该在 DSH 侧做一个带权限模型的审批服务，而不是插件自己做。

## #66 的 C 块（Everything IPC + PowerShell 直连）—— 只保留 es.exe 回落链，IPC 部分不采纳（2026-11-25）

**是什么**：上游分支里为了让 Windows 上的文件名搜索更快，写了一个 `lib/es-query.ps1`（164 行），用 `powershell.exe -ExecutionPolicy Bypass` 直接连 Everything 的 IPC（`WM_COPYDATA`），逆向出 `pack(1)` 查询头与回包偏移。

**为什么不采纳**：

1. **提权执行**：`-ExecutionPolicy Bypass` 是绕过脚本执行策略的开关。一个插件不该在用户机器上这么做，哪怕脚本本身无害——它会把"插件能做什么"的边界推到一个不可审计的位置。
2. **依赖未文档化的二进制协议**：Everything 1.4.1.1026 的 IPC 结构没有公开契约，升级即可能崩；失败时还要回落，收益不稳定。
3. **已有等价能力**：本仓库早已实现 `es.exe` 提供者（`lib/search-docs.js` 的 `es`），走 Everything 官方命令行、失败自动回落 `rg` → `walk`。IPC 只省一次进程启动，不值得。

**保留了什么**：`autoOrder('win32')` 仍是 `['es','rg','walk']`——装了 Everything 命令行工具就优先用它，否则自动回落。本次只修了 `es` 提供者里一句复制粘贴写错的错误文案（原本报 "rg 不支持目录搜索"）。
